# 同分收益与启动交付加固（v0.9）

日期：2026-10-22。基线仍为已核验v1.1.1，参考v1.1.2与赛事书面规则。本轮在Ubuntu虚拟机内编译/验证，Windows的outputs/rmtc-bot是同步源码与交付副本。没有新比赛或付费模型调用，官方裁判不修改。

## 1. 为什么资源封顶后仍要捡资源

第二阶段资源120、有效伤害300后，对应主要分数不再增加；规则同场排名在总分后还比较获资格任务数、原始资源、原始有效伤害、无效动作数。因此“没有主要分数增量”不等于“毫无排名价值”。

这次不用给原始资源乘一个很小的权重。再小的权重也可能累计到超过真实分数或安全代价。候选先按原有主要效用U比较；只有U完全相同，才按预计任务完成、原始资源、有效伤害依次比较。这里是本地规划量，官方排名仍用裁判记录及九位小数规则。

例：安全WAIT和安全采集的主要效用都是0，采集有原始资源增量，可选采集；如果去采集有额外风险，U降到负值，原始资源再大也不能抵消。攻击和移动在本Tick继续承担相同位置的受击假设，防御独立计算减伤。

## 2. 对应代码

- battle的TacticalCandidate增加三个独立次级量，拒绝NaN/Inf/负值；不把它们加进score_points。
- objective在主要资源分封顶后仍可提供原始资源目标；已满足阈值但官方完成ID尚未回填时，不重复预估5分。候选32上限在插入时生效，同格先合并。
- runtime按路线进度折算次级收益，本Tick采集前阵亡则清零移动候选的采集/任务预计收益。balanced保留封顶后的攻击/短程接近比较，collect继续要求正效用及击杀/无反击门槛。
- 新增P5_tiebreak_resource与P7_tiebreak_firing_position日志原因，便于后续核对；没有增加正式decision_type。

13项新同分测试全部通过，覆盖主要收益优先、官方次级顺序、风险不能被原始资源买通、collect门槛、坏数值、封顶采集、延迟任务回填、阵亡不采集、同风险攻击等。battle回归8/8、objective回归8/8；battle累计第三次到上限停止，objective累计第二次。同分组首轮一次，不重跑其他耗尽组。

## 3. 启动前检查为什么不直接运行节点

turing_bot_node新增--check-config，分支在rclcpp::init之前：共享生产配置解析器，但不构造Node、BotRuntime、HTTP或日志线程。成功返回0，错误配置返回2，显式阶段2缺完整AI接入返回3。输出只有阶段、两模式、AI是否已配置、无ROS/网络请求等安全诊断。

tools/preflight.sh/py检查Linux/Humble环境、席位队名、域编号是否提供、网络范围、安装二进制、配置和日志父目录写权限。它不发消息、不探测真实AI、不写配置；直接python运行也禁字节码缓存。通过只能说明本地准备项符合，不能代替有线DDS、官方回执与本场真实AI成功。

run_team.sh使用实际队名“肥鱼说的都队”，支持席位/裁判IP两个参数或环境变量。team-profile.json记录队长蔡礼格、队员李宸梓，分工待确定。

标准启动器按本机ROS域＋席位取得文件锁，节点exec后继承锁；退出由OS释放。域027与27归一，其他席位/域可并行。锁目录/文件拒绝符号链接、错误归属和公开权限。不删除旧锁文件，也不自动重启。绕过启动器的直接二进制启动、其他机器的重复席位仍需运行管理。

新启动组首轮15/15；补充“不带-B直接运行预检也不产生缓存/日志”的边界后第二轮16/16。使用无害假二进制验证exec持锁生命期，用本地监听器确认配置检查无连接。没有启动ROS运行场景，也没有消耗真实模型。

## 4. 独立构建与交付

tools/build_isolated.sh只接受项目内不存在的新目录，拒绝覆盖已有构建，不删除文件、不安装软件。隔离build/install/log，Release、--symlink-install、关闭测试、2个编译作业。实际在delivery-validation/v0.9成功，ros2 pkg prefix指向该独立install，ldd无缺库，配置检查直接退出。

这是现有Ubuntu22.04.5/Humble内的空构建目录验证，不是全新Ubuntu、Docker或OVA恢复。常规启动仍使用contestant_ws/install；独立构建不静默覆盖默认安装。

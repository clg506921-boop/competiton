# 模型输出诊断与离线加固（v0.7）

日期：2026-10-22。继续遵守已核验v1.1.1、参考v1.1.2，以比赛规则和通信协议为准。修改范围仅为自研程序；本轮不启动裁判比赛、不调用真实模型、不修改虚拟机配置。

## 为什么先做这一项

v0.6真实代理场已完成开场调用和500Tick通信，但出现一份事件输出拒收、一次客户端超时后代理成功。旧日志只有拒收总数，没有结束原因、校验层次和字段位置，而且没有保存原始模型回复，因此不能还原那份旧输出究竟哪里不符。

这轮先补上可定位问题的诊断，再做有证据支持的兼容与安全处理。它不能证明旧的真实失败已经解决，也不补造旧请求的原因。

## 请求与输出的处理流程

```text
HTTP请求（后台worker）
  → 记录steady_clock耗时、响应字节数、finish_reason枚举
  → HTTP响应解包
  → 截断/过滤检查
  → 模型JSON清洗
  → 整体结构校验
  → 逐事件Schema与来源/关联/坐标/时间校验
  → 仅传递解释结果和有界诊断给控制线程
  → 按原公告观察Tick合并事件记录
```

原始裁判公告仍只进行传输分帧、完整正文去重和Prompt封装。这里解析的对象是模型回复，不在本地从公告的词句推断事件。

`HttpReply`增加模型结束原因、响应字节数、请求耗时。结束原因只保留`unknown/stop/length/content_filter/other`，不把供应商返回的任意字符串写入日志。耗时范围包含transport发送、接收和HTTP JSON解包，不包含后续事件语义校验，也不含排队等待。

`decode_chat_completion()`可离线测试，实际libcurl路径也调用同一实现。HTTP200仍按原规则占用成功额度；没有因此重发被截断或格式错误的2xx。`length`即使返回片段恰好是一个完整JSON，也不用于事件决策；`content_filter`同样不采用。

模型原文在worker完成校验后释放，不随结果队列传入控制线程。网络、JSON清洗和语义校验都留在worker，控制线程继续读取已完成的结果，不等待网络。

## 诊断状态与字段

| 字段 | 含义 |
| --- | --- |
| ai_request_ms / ai_response_bytes | 最近消费结果对应的请求耗时/HTTP响应体字节数 |
| ai_finish_reason | 白名单结束原因；缺省不是擅自当成stop |
| model_output_state | 未请求事件、传输错误、空内容、截断、过滤、解析拒绝、整体结构拒绝、条目拒绝、部分接受、未解决、无事件、已验证或校验异常 |
| model_parse_detail | 固定解析错误码，如对象不完整、重复键、超深嵌套；不含回复原文 |
| model_rejection_field | 来自固定Schema的字段路径，如`root.events[0].params.damage`，不含模型给的额外键名或值 |
| model_rejected_envelope/schema/source/link/geometry/time | 最近一份结果分层拒绝计数；每个条目只报告首个失败类别 |
| model_event_accepted / model_unresolved / model_ignored_fields | 最近一份结果的结构/语义接受数、合法未解决来源数、忽略额外键的数量 |
| model_observed_tick / model_consumed_tick | 原公告观察Tick与控制线程消费解释的Tick，资格请求使用-1 |
| model_events_validated_total / model_events_merged_total | 当前进程累计接受条目数/合并记录数；合并历史事件不等于当前效果生效，也不等于动作已执行 |
| model_events_ignored_total / model_unresolved_total / model_truncated_total | 当前进程累计首次合并未应用的条目数、未解决来源数、截断回复数 |

最新结果字段在换session时清空，累计字段在同进程内保留。旧generation结果不进入新场诊断、事件记录或本场成功标记；同一令牌的调用额度仍保留。每Tick日志会重复最新状态，不能把日志行数当成HTTP次数；调用次数看`ai_attempts/ai_successful/ai_uncertain_reserved`和裁判记录。

资格请求只做公开任务摘要，不按事件Schema解析，记录为`not_requested`。`validated`只表示有条目通过且没有拒绝；同时有好坏条目为`partially_accepted`，全坏为`items_rejected`，不把“执行了校验”写成“校验通过”。

## 兼容处理与Prompt

原有代码块包裹、最外层单个JSON对象、忽略额外键、补齐缺省nullable字段继续保留。这次新增开头UTF-8 BOM处理，重复JSON键单列诊断。数字字符串不转成数字，缺少必需参数不补默认值，越界坐标、外部来源/关联和矛盾时间仍拒绝。

Prompt补充最小合法外层示例、最多4事件、各类型trigger对应关系。缺少必需事实时返回`events=[]`及`unresolved_source_ids=[source_id]`，不输出缺参数的forecast。公告原文保持不变，未知发生时间仍为null。

没有添加供应商专有thinking开关，没有更改10/25秒超时、L约束、最多两次发送、35秒未知占位或正式模型接入规则。真实模型能否按此Prompt稳定输出仍需后续实测；不能以本轮单测代替。

## 线程异常处理

transport若抛出异常，以固定`transport_exception`返回一条可观测结果，异常正文不记录。由于无法知道是否已经发出，保守占用一个未知额度并按既定冷却处理，避免worker只停止而没有诊断；代价是某些本地失败可能少用一次额度。线程入口和回调原有try/catch保留。

## 验证与次数

新增`model_diagnostics_tests`最终包含17项：结束原因白名单、空内容与解析失败区别、截断/过滤不应用、重复键、BOM与额外键保密、必需参数路径、Tick类型、来源/关联/坐标/时间分类、部分接受、多事件错误项下标、未解决来源、传输/资格区分、请求计时和原文释放、transport抛异常、慢模型期间继续控制与过期爆炸不重新生效、旧场结果隔离、Prompt契约。

第一次15/16：换场测试在旧场只沉默一个500ms周期时就要求切场，违反现有两周期门控。修正夹具时间至1000ms后第二次16/16通过；没有修改生产换场门控。同时消除夹具的缩进编译警告。首次失败结果与日志保留。

复查发现逐项校验时，错误字段路径会把第二个坏条目也标成`events[0]`。修正为原数组下标，并加入第17项；第三次17/17通过。该组累计3次，到上限停止，不重命名重置次数。

有余量的事件组回归9/9通过（含24份审核样例的期待检查），该组累计第3次，到上限停止。实际libcurl的本地假HTTP回归4种响应通过，累计第2次。这两组在诊断下标修正前通过；下标修正不改接受条件，最终新增17项验证了该路径，再重编全部目标与ROS节点，没有重跑耗尽组。原LLM、core、advanced、opportunity及隔离综合场景也未重跑。

全部C++目标与ROS编译的最终状态、源码哈希、官方程序完整性及进程清理见`evidence/model-diagnostics-verification-2026-10-22.json`。本轮没有新的ROS运行场景，当前构建的ROS节点也没有新比赛成绩；v0.6比分只属于历史已测版本。

## 后续实测验收方式

在获得额外测试额度后，经原裁判代理发送受控真实事件请求，分别检查：本场真实成功、模型结束原因、事件接受/拒收分类、解释完成时的Tick、实际动作及官方回执。第二阶段三场额度保持已用完，本轮不自动开启第四场，也不把改名或换版本当作新额度。

本轮完成的是诊断和离线加固。v0.6真实输出的拒收根因仍待下次带诊断的请求确认；真实八类事件闭环、24×24第二阶段、有线异机DDS、镜像及检录材料仍在待完成清单。

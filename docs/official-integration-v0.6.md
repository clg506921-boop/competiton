# 官方裁判联调与任务路线优化（v0.6）

日期：2026-10-22。基线为已核验 v1.1.1，参考 v1.1.2；比赛规则与通信协议优先。源码与构建位于 Ubuntu 虚拟机 `/home/ubuntu/projects/RMTC/contestant-v0.1`，Windows 的 `outputs/rmtc-bot` 是同步交付副本。

## 这轮完成的功能

正式接入官方练习裁判，检查自研程序的感知、动作、下一帧 `self.last_action`、完整成绩和退出。测试控制器单独位于 `tools/run_official_trial.py`，可以查看练习全图和分数用于验收；这些信息不进入参赛节点。参赛节点仍只读取本席位公开感知。

每场启动前、退出后核对官方16文件与原始压缩包哈希；官方程序、规则、内置地图和配置不修改。地图尺寸补测使用自研目录内的外部配置，通过官方 `--config` 接口加载。

第二阶段原来先做 reach，再处理采集任务。在四车争抢中，远处 reach 会耽误近处高价值资源，之后资源被别人拿走，就无法补完任务。新增 `objective.hpp/.cpp`，把未完成的到达、普通资源、高价值资源、累计价值任务放进同一层比较：

1. 用已知地图的 BFS 路径距离计算可达性，排除软终局前来不及到达的目标。
2. 资源收益按第二阶段官方封顶函数计算，任务收益每项最多5分；数量进度只是本地规划估值，完成状态以官方 completed IDs 为准。
3. 同一格的任务和资源合并；两站路线整体计算收益，避免重复计入同一任务的5分。
4. 最多32个候选，保留8个首站，第二站前瞻权重0.25；按首站缓存 BFS 距离，减少重复搜索。
5. 前瞻只影响目标排序。共同风险比较只计算下一目标的直接收益，继续统一比较攻击、移动、防御的受击风险。

第一阶段采集分支保持原有算法。任务坐标、资源和地图来自感知，没有写死练习目标。

## 验收工具自身的修正

第一阶段独立Python观察器只录到了96条动作，首次把观察缺失当成了程序丢动作。进一步核对本程序ROS订阅日志中的实际官方 `last_action`：100个动作均有对应回执；观察器缺失的4条动作都有成功MOVE回执。

没有为这个差异重跑比赛，也没有降低99%的验收阈值。保留首次错误判定与只读复核结果，把“本节点收到的官方执行回执”和“额外观察器的记录覆盖率”分别列出。主证据为100/100；独立观察器覆盖不足仍如实记录在JSON中。

## 时间与机器负载

内置第一阶段收到回调到发布动作的内部 p99 为2.441ms，最大2.814ms。第二阶段基线内部 p99 为3.853ms，优化候选为18.386ms，候选最大82.896ms。测量范围不含上游DDS和裁判结算。

裁判固定CPU0、1，自研节点CPU2、3；三辆官方陪练继承裁判CPU。虚拟机曾有soft lockup和NEM计时滞后，第二阶段四车数据用来验功能，不据此得出性能优劣。真实流逝时间也长于理论时长；不能把内部p99当成端到端时延保证。

## 真实模型接入

使用用户自有DeepSeek账户，经未修改的裁判练习代理转发。密钥通过标准输入注入测试进程，只保存在进程内存/裁判子进程环境；参赛节点只收到本地练习席位令牌。源码、笔记、命令行参数和提交包不保存真实密钥。

一次独立代理探测成功：HTTP200、返回非空，约0.997秒，63个tokens。该探测暂停在Tick0，不是生产节点联调；使用了仅限探测的关闭思考选项。生产节点没有加入该供应商专有字段，因此不能把探测时间直接当成生产请求时延。

生产节点另进行一场真实代理联调，调用预算最多3，不启用会自行调用模型的官方陪练。练习模型、输出额度与本地调用配额属于此测试配置，不能沿用成正式公告参数。最终结果见本页后续记录及 `evidence/official-campaign-v0.6-2026-10-22.json`。

当前DeepSeek模型名与请求字段以[官方API文档](https://api-docs.deepseek.com/api/create-chat-completion/)及[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)为依据。正式比赛仍使用主办方公告的模型、网关、L与本场令牌。

## 最终补测结果

生产节点真实代理场完整结束于Tick500：裁判分55.0，资源120.0，伤害200.0，任务3，无效动作0。未启动陪练AI，因此不能与四车场比较胜负。500个有效窗口决策均有关联回执。

开场任务请求在Tick4前观察到HTTP200；代理共记录3次真实成功。节点在10秒超时前收到其中2次，另1次记为未知预留，之后由代理完成；节点预算2次成功＋1次预留=3，与代理实际3次相符，没有继续发送。独立探测1次加生产3次，本轮总计4次真实上游请求；账单金额未查询。

事件来源notice-1的返回使model_rejected增加1；notice-2客户端超时。没有保存原始模型回复，当前日志也没有逐事件接受计数，因此不能确定拒绝发生在JSON格式还是字段语义，不能断言八类事件解释已成功，更不能把HTTP成功写成事件动作闭环成功。这是本轮新发现、保留待解决的问题。后续应增加无敏感正文的校验原因与接受计数，再在额度允许时做受控真实事件复验；本轮不因失败自动再开第四场第二阶段。
